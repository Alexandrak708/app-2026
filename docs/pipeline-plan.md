# University Research Agent — Implementation Plan

> A coding agent specification for an autonomous Gemini Flash-powered pipeline
> that discovers and researches universities in any city without hardcoded paths.

---

## Goal

Build an agentic loop where Gemini Flash acts as an autonomous research agent.
It receives only a city name, decides on its own which URLs to visit and which
queries to run, and outputs structured university data into Supabase — matching
the existing schema by reading live rows as examples.

---

## Core Principle: No Hardcoded Paths

The agent must never have fixed strings like `/admissions`, `/programs`, or
`"universities in {city}"` baked into the code. Every search query and every
URL is generated by Gemini at runtime based on what it has already found.

---

## Architecture: Agentic Loop

```
Input: "Varna, Bulgaria"
        ↓
 [ Gemini thinks ]  ←──────────────────────┐
        ↓                                  │
 Choose action:                            │
   search(query)                           │
   fetch_page(url)                         │
   save_university(data)                   │
   done()                                  │
        ↓                                  │
 Execute action via Firecrawl              │
        ↓                                  │
 Return result to Gemini ──────────────────┘
        ↓ (when done() called)
 Output: universities saved to Supabase
```

Each iteration Gemini receives the full conversation history (all previous
actions and results) so it can reason about what it already knows and what is
still missing.

---

## Phase 1 — Discovery

**Objective:** Find the names and websites of ALL universities in the city.

### What the agent receives
- City name and country (e.g. `"Varna, Bulgaria"`)
- The three available tools (see Tool Definitions below)
- A system prompt describing its role and stopping criteria

### What the agent does on its own
1. Generates its own initial search queries — no queries are provided by the code
2. Evaluates results — distinguishes real university websites from aggregators,
   ranking sites, and Wikipedia
3. Extracts domains of confirmed universities
4. Generates follow-up queries if it suspects missing results (e.g. searches in
   the local language, searches for "academy", "college", "institute" variants)
5. Stops when two or three consecutive search rounds yield no new universities

### Stopping criteria (in system prompt)
- At least one search round completed
- Two consecutive rounds with zero new universities found
- OR a maximum iteration cap reached (recommended: 20 iterations for discovery)

### Output of Phase 1
A list of objects: `{ name, website }` — passed directly into Phase 2.

---

## Phase 2 — Deep Research

**Objective:** For each university, extract full structured data.

Runs after Phase 1. Can be parallelised — each university is independent.

### What the agent receives per university
- The university name and homepage URL from Phase 1
- The three tools
- A system prompt describing what data to extract
- The Supabase schema (see Schema Reference below)

### What the agent does on its own
1. Fetches the homepage and reads navigation links and sitemap hints
2. Decides which sub-pages to visit based on their link text and context —
   not based on hardcoded path guesses
3. Visits those pages, reads the content, and decides if more pages are needed
4. Extracts all available information
5. Calls `save_university` when it has enough data, or when the iteration cap
   is reached

### Stopping criteria (in system prompt)
- All target data fields are populated, OR
- Three consecutive fetches yield no new information, OR
- Maximum iteration cap reached (recommended: 15 iterations per university)

---

## Tool Definitions

These are the only three tools the agent can call. The code executes them;
Gemini only decides when and with what arguments.

### `search(query: string)`
- Calls Firecrawl search
- Returns: array of `{ url, title, description }` (top 5–8 results)
- Used in both phases

### `fetch_page(url: string)`
- Calls Firecrawl scrape on a specific URL
- Returns: markdown content of the page
- Used in Phase 2

### `save_university(data: object)`
- Validates the object against the Supabase schema
- Reads 3–5 live rows from Supabase as format examples
- Inserts the new row if no duplicate exists (match on `name` + `city`)
- Returns: `{ success, id }` or `{ skipped, reason }`

## System Prompts

### Discovery system prompt
```
You are a research agent. Your goal is to find ALL universities, colleges,
academies, and higher education institutions in {city}, {country}.

You have three tools: search, fetch_page, save_university.

Strategy:
- Start with broad searches. Generate your own queries — vary the language,
  try local language variants, try different institution type keywords.
- Evaluate each result: is this a real institution website or an aggregator?
  Only keep official institution domains.
- Keep track of what you have found. Stop searching when two consecutive
  rounds produce no new institutions.
- Do NOT call save_university in this phase. Only collect names and websites.
- When done, call done() and return the list as JSON.

Maximum iterations: 20.
```

### Deep research system prompt
```
You are a research agent. Your goal is to extract structured information
about {university_name} from its website: {homepage_url}.

You have three tools: search, fetch_page, save_university.

Target data:
- Official name and local-language name
- Description (2–3 sentences)
- Admissions email
- Programs: name, level (bachelor/master/phd), duration, language,
  tuition per year, currency, study mode (full-time/part-time/online/hybrid)
- Admissions: deadlines, requirements, application URL
- Scholarships: name, amount, eligibility
- Languages of instruction
- Accreditations
- Year founded

Strategy:
- Fetch the homepage first. Read the navigation to understand the site structure.
- Choose sub-pages to visit based on what their links suggest — do not guess paths.
- Stop fetching when you have sufficient data or three pages in a row add nothing new.
- Call save_university when done.

Maximum iterations: 15.
```

## Loop Implementation

### Pseudocode

```
function run_agent(system_prompt, initial_user_message, tools):
    history = [
        { role: "system", content: system_prompt },
        { role: "user",   content: initial_user_message }
    ]
    iteration = 0

    while iteration < MAX_ITERATIONS:
        response = gemini.generate(history, tools)

        if response.type == "text" and response.text contains "done":
            return parse_final_output(response.text)

        if response.type == "tool_call":
            tool_name = response.tool_call.name
            tool_args = response.tool_call.arguments

            result = execute_tool(tool_name, tool_args)

            history.append({ role: "model",  content: response })
            history.append({ role: "tool",   content: result })

        iteration++

    return whatever_was_saved_so_far
```

### Key implementation notes

**Full history on every call** — Gemini has no memory between API calls.
Always pass the complete history so it knows what it has already done.

**Loop protection** — hard cap on iterations per phase. If the cap is hit,
log a warning and move on; don't let one difficult university block the rest.

**Parallelisation** — Phase 1 is sequential (each search builds on the last).
Phase 2 can run all universities concurrently with `Promise.all`, since each
university is independent.

**Tool call format** — Gemini Flash supports native function calling. Define
tools using the Gemini function declaration schema. The model returns a
`functionCall` part; you execute it and return a `functionResponse` part.

**Deduplication** — `save_university` checks existing rows before inserting.
Match on normalised name (lowercase, trimmed) + city to avoid duplicates from
Phase 2 re-runs.

## Schema Reference

Current `universities` table columns (from live Supabase data):

| Column | Type | Notes |
|---|---|---|
| `id` | uuid | Generated by Supabase — do not include |
| `name` | text | Official English name |
| `country` | text | |
| `city` | text | |
| `website` | text | Homepage URL |
| `admissions_email` | text | Null if not found |
| `description` | text | 2–3 sentence summary |
| `created_at` | timestamp | Generated by Supabase — do not include |
| `updated_at` | timestamp | Generated by Supabase — do not include |

The agent reads 3–5 live rows before each insert so it always mirrors the
exact format of existing data.

## File Output Structure

```
cities/
  {city-slug}/
    _discovery.json      ← raw list from Phase 1
    {uni-slug}.json      ← extracted data per university (before DB insert)
    _run_log.json        ← iteration counts, errors, skipped universities
```

These files serve as a cache — if a `.json` file already exists for a
university, Phase 2 skips the research and goes straight to `save_university`.

## Usage (final CLI interface)

```bash
# Research one city
node agent.js "Varna" "Bulgaria"

# Limit to discovery only (no deep research)
node agent.js "Sofia" "Bulgaria" --discovery-only

# Skip discovery, re-run deep research for existing _discovery.json
node agent.js "Berlin" "Germany" --research-only

# Dry run — no Supabase inserts
node agent.js "London" "UK" --dry-run
```

## What the Coding Agent Should Build

1. `agent.js` — entry point, parses CLI args, orchestrates phases
2. `tools.js` — the three tool implementations (search, fetch_page, save_university)
3. `loop.js` — the agentic loop function (reusable for both phases)
4. `prompts.js` — system prompts for discovery and deep research phases
5. `supabase.js` — Supabase client, read examples, insert with dedup check
6. `package.json` — dependencies listed above, `"type": "module"`
